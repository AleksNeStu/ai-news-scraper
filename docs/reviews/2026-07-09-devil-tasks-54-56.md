## Detail

### MAJOR findings

#### F1 — `top_k` vs `page_size` router contract violation (CALL-OUT 2, Task #58)

`apps/api/api/routers/search.py:49-53`

```python
def _resolve_page_size(payload: SearchRequest) -> int:
    """Effective page_size, honouring the deprecated `top_k` synonym."""
    if payload.top_k is not None:
        return payload.top_k
    return payload.page_size
```

But `apps/api/api/schemas/search.py:61-69` claims the opposite in its validator:

```python
def _no_both_top_k_and_page_size(self) -> "SearchRequest":
    if self.top_k is not None and self.page_size != 10:
        # Caller set both — prefer the explicit page_size, warn in log.
        logger.warning(
            "search: top_k=%s ignored, page_size=%s used",
            self.top_k,
            self.page_size,
        )
```

**The validator logs "page_size wins" while the router returns `top_k`.** Whichever
end is correct, the two halves of the contract disagree. The new test
`test_search_top_k_wins_over_page_size_when_both_are_set` (lines 278-298 in
test_search.py) pins the current (router-side) behaviour. The validator's log
message will continue to lie to on-call until Task #58 lands.

**Action:** Tracked as Task #58 (high priority, pending). Do **not** attempt to
fix in this PR — that was the brief's explicit instruction. The CALL-OUT
comment in the test makes the discrepancy discoverable without re-running the
search.

`apps/api/api/routers/search.py:113` (the live formula) vs the pre-`4173ba6`

- T1: `min(max(1*10*2, 1*10+50), 1000)` = `min(70, 1000)` = 70 — but the

- T2: `max(20, 60)` = 60 ✓
- T3: `max(1980, 1040)` = 1980, `min(1980, 1000)` = 1000 ✓
- T4: `max(14, 57)` = 57 ✓
- T5 (top_k=7, page_size=3): resolves `page_size=7` (F1), then
  `max(14, 57)` = 57 ✓
- T6 (p=100,101, ps=10): both `min(>1000, 1000)` = 1000 ✓

All five math results verified independently. The MAJOR is the **drift itself**
— assertions silently broken for an unknown number of merges between `4173ba6`

**Action:** Already documented in the test file's three CALL-OUT comments

### MINOR findings

#### F3 — Dangling `FACETS_STALE_MS` reference in code comment

`apps/web/src/app/[locale]/(app)/search/SearchClient.tsx:76`

```ts
// Facets are fetched once on mount and held for FACETS_STALE_MS. URL
// changes (source/topic/from/to/page) deliberately do NOT re-trigger
// the fetch — the taxonomy is library-wide, not query-scoped — so the
// same `searchFacets` cache-key (facets:{user_id}) on the server is
// reused until either the TTL elapses or this component unmounts.
```

`FACETS_STALE_MS` is **not defined anywhere** in the file or codebase.
The actual behaviour is "fetched on mount, held until unmount" — there is
no client-side TTL. The comment was probably cut-and-pasted from a draft
that planned to add a re-fetch timer. The mount-only effect at line 86
*does* match the comment's intent, but the named constant is a lie.

**Action:** Drop the "held for FACETS_STALE_MS" clause in a 1-line follow-up
commit, or define the constant. Cosmetic, not a blocker.

#### F4 — Silent catch block in facets effect

`apps/web/src/app/[locale]/(app)/search/SearchClient.tsx:98-108`

```ts
.catch((e) => {
  // Swallow aborts; surface real failures only when relevant. For
  // the MVP the facets panel renders as empty lists on failure
  // rather than blocking the page (Task #54 scope: do not break
  // the existing /search UX if /search/facets is down).
  if (ctrl.signal.aborted) return
  if (!(e instanceof ApiError)) return
  // 401/5xx → user-not-signed-in or backend hiccup. The search
  // form keeps working; the empty filter widgets are an acceptable
  // degraded state.
})
```

After the two early-returns, the function falls off the end and *silently*
swallows every ApiError. No `console.error`, no telemetry, no log. If
`/search/facets` is broken in production, the only signal is "users see
empty filter dropdowns" and the only paper trail is the server's own
access log.

**Action:** Add a single `console.warn('[facets] fetch failed', { status: e.status, message: e.message })` in the ApiError branch. Fits the "degrade silently in UI, log loudly in console" pattern the codebase already uses for
the searchArticles error path (line 162). Cosmetic, not a blocker.

## TanStack Query deviation adjudication
**Deviation justified; `useEffect + AbortController` is functionally equivalent.**
Searched the entire `apps/web/src` tree — there is **no** `QueryClientProvider`
and **no** `@tanstack/react-query` import anywhere. The Architect's hand-off
listed `useQuery` as the recommended approach *if* the provider were in
place, but the codebase is currently zero-React-Query. Adding a
`QueryClientProvider` to the root layout to switch to `useQuery` for a
single mount-only call would be a larger architectural change than the
task scope justifies. The chosen pattern (`useEffect([])` with
`AbortController` + `ctrl.signal.aborted` guard + `api.get` forwarding
`init.signal`) hits every functional requirement: single mount-time fetch,
abort-on-unmount, no refetch on URL change, no race condition. **No
follow-up commit recommended.**
