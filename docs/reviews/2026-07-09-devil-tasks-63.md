## A. Verdict — **GO-with-conditions**

The fix is correct, minimal, and isolated to the test file. The flake root cause
(httpx cookie-jar merge with per-request `cookies=` kwarg) is correctly
identified, and the chosen fix (send via `Authorization: Bearer` header) is the
right shape — it sidesteps the merge entirely because `_extract_token` checks
Bearer FIRST (`apps/api/api/deps/__init__.py:35-36`).

The 5-case regression matrix is well-constructed, with good isolation reasoning
per case. All 5 use the same Bearer-header pattern as the fixed original.

**One HIGH finding below (Finding 1)** — the matrix omits a JWT-attack class
the Architect spec explicitly listed as a sub-case (the canonical
`alg=none` downgrade). This is a 5-line fix and should land as a follow-up
in the same PR (or right after) so the regression matrix actually proves
defense against the most-named JWT downgrade attack. Without it, the
matrix is missing the attack class its own docstring cites.

Three MEDIUM / LOW findings cover: a coverage-duplication concern (case 4 vs
the original test), a hermeticity concern in cases 1-4 (no real `register`
call), and a separate but related `test_auth_hardening.py` smell that
should be filed as Task #64 follow-up (not blocking).

No CRITICAL findings. No production code touched. No `conftest.py` touched.
Test-helper symbols (`_b64url`, `_now_exp`) are new and don't shadow
existing fixtures.

## B. Findings (ranked CRITICAL -> LOW)

### Finding 1 — **HIGH** (coverage gap on `alg=none` downgrade)

- **File / lines:** `apps/api/tests/test_auth.py:369-393`
  (`test_me_rejects_jwt_with_wrong_algorithm`).
- **Defect:** The test exercises `alg=HS512` against an `HS256` allow-list,
  which is the *alg-mismatch* class. The Architect's §C table (line 102-105
  of the review doc) explicitly lists `alg=none` as **sub-case 2a** and
  the test docstring at `apps/api/tests/test_auth.py:374-376` even calls
  it "the canonical defence against the `alg=none` downgrade attack" —
  but the test never actually forges an `alg=none` token. So the
  docstring is selling a guarantee the test does not prove.
- **Failure scenario:** A future regression that loosens
  `algorithms=[_settings.jwt_algorithm]` to a permissive set (e.g.
  a refactor that uses `jwt.get_unverified_header()` for inspection
  before verifying) could allow `alg=none` tokens through. The current
  matrix would not catch it — the `HS512` test exercises a
  *signature-algorithm* mismatch, which is structurally a different
  bypass than `alg=none` (no-sig-no-key).
- **Suggested fix:** Add a 6th case (or a parameterized loop) that mints
  `{header: {"alg": "none", "typ": "JWT"}, payload: {...}}.` (empty sig,
  `alg=none`). Expected: 401. PyJWT's `decode(..., algorithms=["HS256"])`
  raises `InvalidAlgorithmError` on `alg=none` because `none` is not in
  the allow-list — the test will pass. Five extra lines.
- **Why HIGH not MEDIUM:** The test docstring makes a security claim
  ("canonical defence against the `alg=none` downgrade attack") that the
  test does not actually verify. That's a coverage-vs-claim drift on a
  security-critical invariant; CI-stable means the test that names the
  attack actually proves the defense.

### Finding 2 — **MEDIUM** (case 4 "swapped payload" overlaps the original test)

- **File / lines:** `apps/api/tests/test_auth.py:421-460`
  (`test_me_rejects_swapped_payload`).
- **Defect:** The test docstring claims it "is the same surface as the
  original `test_me_with_tampered_jwt_returns_401` but with the violation
  localised to the payload segment (proves the dep actually re-verifies
  the payload digest — not just the signature bytes)." Mechanically
  though, both tests end up at the same PyJWT error path
  (`InvalidSignatureError` on HMAC re-compute) because PyJWT always
  HMAC's `head.payload` together — you cannot flip *only* the payload
  without breaking the signature. The test therefore re-tests the same
  thing the original test already covers, with extra setup.
- **Failure scenario:** None — this is a coverage-duplication smell, not
  a correctness bug. Risk: a future maintainer deletes one of the two
  tests as "duplicate" and accidentally narrows the matrix.
- **Suggested fix:** Either (a) keep the test but rewrite the docstring
  to honestly describe what it covers (e.g. "tampered sig segment
  produced by mutating the payload — confirms the verification path
  re-HMAC's the supplied payload, not a cached one"), or (b) drop the
  test and add a comment in the original test pointing to it. Pick one.

### Finding 3 — **MEDIUM** (cases 1-4 are not hermetic — no real `register`)

- **File / lines:** `apps/api/tests/test_auth.py:347-460` (cases 1-4).
- **Defect:** Cases 1, 2, 3, 4 do not call `auth_client.post("/auth/register", ...)`
  before forging the token. The dependency at
  `apps/api/api/deps/__init__.py:47-69` resolves the user UUID via
  `payload.get("sub")` but never queries the DB inside the `get_current_user_id`
  dep — the user existence check happens in the *route handler*, not the
  dep. The test still works because the dep raises 401 at the dep layer
  before the route runs.
- **Failure scenario:** The tests pass today because the dep short-circuits
  on the violation before any DB hit. If a future refactor moves the
  `sub` -> user lookup into the dep (a plausible optimization: avoid
  one DB roundtrip on every authenticated request), cases 1-4 would
  start failing with 401-with-different-detail (user not found) instead
  of the violation-specific 401 — and worse, the tests would still pass
  with a generic 401, hiding the regression. Cases 5 and the original
  tampered-sig test do call `register`, so they would catch the shift.
- **Suggested fix:** Either (a) add a real `register` call before
  forging the token in cases 1-4 (re-using `auth_user` fixture from
  `conftest.py:116-145` would be cleanest), or (b) explicitly document
  in each test docstring why hermeticity is not required ("dep raises
  before DB hit, so user existence is irrelevant").

### Finding 4 — **MEDIUM** (isolation smell: `test_auth_hardening.py` H3 tests use `cookies=`)

- **File / lines:** `apps/api/tests/test_auth_hardening.py:452-453, 492,
  496, 517, 543-544` — `test_refresh_rotates`, `test_stale_refresh_returns_401`,
  `test_logout_revokes_refresh`, `test_unknown_refresh_returns_401`.
- **Defect:** Out of scope for the diff, but related: these H3 tests pass
  both `auth_token` and `auth_refresh` via `cookies={...}` kwarg, which
  is the same merge pattern the Architect identified as the flake root
  cause for the `test_me_with_tampered_jwt_returns_401` test. The H3
  tests don't appear to flake today because (a) they don't *also* rely
  on the client jar's existing auth_token, and (b) FastAPI's
  `Cookie(default=None)` dep behaves the same way (first-match-wins on
  duplicate names). The risk is in the OPPOSITE direction: if a future
  test in the same `client` instance leaves an `auth_refresh` cookie
  in the jar, the merge on a subsequent test could route a leftover
  valid refresh token into a "replay" test that asserts 401, instead
  passing. The `test_stale_refresh_returns_401` test is the most
  exposed — it does TWO `post("/auth/refresh", cookies=cookies)` calls
  on the same client, and the jar accumulates `auth_token`/`auth_refresh`
  from the response of the first call.
- **Failure scenario:** A future reorder of the test file puts a
  register-then-logout test before `test_stale_refresh_returns_401`,
  and the stale-replay test starts seeing the rotated token from the
  prior call instead of the original. Low probability today; rises as
  the suite grows.
- **Suggested fix:** Out of scope for the current PR — file as
  Task #64 follow-up. The fix is mechanical: either pass cookies via
  the `Cookie:` header (httpx `headers={"Cookie": ...}`) which does
  NOT merge, or call `auth_client.cookies.clear()` before each H3 test
  that uses `cookies=`. Not blocking the current PR.

### Finding 5 — **LOW** (the `_b64url` helper sorts keys)

- **File / lines:** `apps/api/tests/test_auth.py:334-337`.
- **Defect:** The helper does `json.dumps(payload, separators=(",", ":"), sort_keys=True)`.
  This is fine for the helper's own use (it encodes a single payload and
  the JWT spec doesn't mandate key order in the payload's JSON), but
  it is not a 1:1 substitute for what PyJWT does internally when it
  re-encodes for HMAC compute. If a test ever needs to encode a payload
  that PyJWT itself produced (e.g. round-trip a real token's payload to
  recompute the sig), `sort_keys=True` will produce a different byte
  string than the original. The test does not currently do that, so
  the issue is latent.
- **Failure scenario:** None today. Future maintainer adds a
  round-trip test that re-signs a real token after payload mutation;
  the sig check fails because `sort_keys=True` reorders the dict.
- **Suggested fix:** Either drop `sort_keys=True` (use the default
  insertion order), or add a comment that the helper is for
  encode-only tests, not round-trip. Not blocking.

### Finding 6 — **LOW** (test imports `jwt` and `base64`/`json` at top level)

- **File / lines:** `apps/api/tests/test_auth.py:28-34`.
- **Defect:** Cosmetic. The new helpers bring in `base64`, `json`,
  `datetime`, and `jwt` at module scope. `jwt` is already in
  `apps/api/pyproject.toml` (it's a runtime dep), and the stdlib
  imports are free. No new transitive dep, no pinning risk.
- **Failure scenario:** None. Future Python version drop could move
  `jwt` to a transitive; not relevant today.
- **Suggested fix:** None — left for visibility.

### Finding 7 — **LOW** (Architect's `auth_user` fixture not reused)

- **File / lines:** `apps/api/tests/test_auth.py` (cases 1-4) vs
  `apps/api/tests/conftest.py:116-145` (the `auth_user` fixture).
- **Defect:** The `auth_user` fixture in `conftest.py:139-145` already
  mints a real, signed, in-DB token via `create_token(user.id, user.email)`
  — exactly what the regression matrix needs for cases 1-4. The matrix
  re-encodes payloads with `_b64url` and re-signs with
  `jwt.encode(payload, _settings.jwt_secret, ...)` — duplicating the
  setup. Reusing `auth_user` would (a) eliminate Finding 3 (hermeticity)
  for free, and (b) reduce per-test setup by ~6 lines per case.
- **Failure scenario:** Future drift between the in-test payload shape
  and what `create_token` actually produces (e.g. an `aud` claim is
  added to real tokens, but the test-only tokens don't have it).
- **Suggested fix:** Refactor cases 1-4 to use the `auth_user` fixture
  as the base token and mutate the resulting JWT in-place. Not blocking.

## E. Top concerns for PM

1. **The docstring sells a guarantee the test does not prove.** The
   `alg=none` case is named in the docstring of
   `test_me_rejects_jwt_with_wrong_algorithm` but not actually tested
   (Finding 1). Either add the test or rewrite the docstring.

2. **The regression matrix is solid but not hermetic.** Cases 1-4
   forge tokens without registering a user; they pass because the
   dep short-circuits on the violation before any DB hit. If a
   future refactor moves the user lookup into the dep, the tests
   would still pass (with 401) but would no longer pin the
   violation-specific 401. Add a `register` call (or use
   `auth_user`) to make the matrix hermetic against that refactor
   (Finding 3 / 7).

3. **The `test_auth_hardening.py` H3 tests are the same shape that
   just flaked.** Out of scope for this PR, but `test_refresh_rotates`
   and `test_stale_refresh_returns_401` use the same `cookies=` merge
   pattern that caused the original flake. If the H3 tests have not
   flaked yet, it's only because no test in the same `client`
   instance has set conflicting `auth_refresh` cookies. File as
   Task #64 (Finding 4).

4. **The 5-case matrix is a foundation, not a ceiling.** 5 of the
   ~10 plausible JWT attack classes are covered. The other 5
   (`alg=none`, malformed-`sub`, `iat` future-skew, large payload,
   cross-claim forgery) are documented above. PM should align with
   the user on which ones need production-code change vs
   documentation-only vs follow-up tests before declaring the
   task fully shipped.

5. **No production code touched, no `conftest.py` touched, no
   fixtures shadowed.** The fix is minimal and surgical. The
   only architectural concern is the `iat` future-skew
   decision (item 6 in §D) — everything else is test-side.
